# Rental notifications

Sign in and open the header bell. Notifications link to the exact conversation, rental invitation or bill. Read one by opening it, or mark the updates seen at the time the panel loaded as read. The bell refreshes while the page is visible, on focus, and after a browser push. New arrivals are not silently marked read by an older request.

New real inquiries and owner/renter messages notify the other party. Demo inquiries and reviewer messages do not create alerts. Rental invitations target the original inquiry account, or the verified email for a manual invitation; the first verified account that opens an email invitation claims its notification history. Owners receive acceptance/decline updates. Renters receive new bills, owner-confirmed receipts, correction requests, reversals and bill cancellations. Notifications are general prompts: the destination record remains the authority for its current state.

Rent reminders run on the existing five-minute Worker schedule, using Philippine dates. Each unpaid bill can receive a reminder three days before its due date, on its due date, and one and seven days late. Pending reports, settled/cancelled bills and closed rental connections suppress reminders, including queued reminders that have not been sent. No daily repeated overdue reminders are sent. Newly created bills receive their own bill alert rather than a second reminder on the same day. There is no historical-message backfill when this feature is deployed.

## Phone and browser alerts

Choose **Turn on notifications** in the bell, then approve the browser permission. No permission prompt appears on page load. HTTPS and a browser with the Push API are required; use Chrome on Android for the first physical-device check. iPhone/iPad users need a supported home-screen web app. Each browser/device opts in independently. The optional **Send test alert** action targets only the current device and is limited to five per account per day, at least a minute apart. The result says queued, not delivered.

Browser push uses native Web Push with RFC 8291 encryption and RFC 8292 VAPID identification; no paid messaging service, SMS or email provider is activated. Store `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` (`mailto:` operator contact) as Cloudflare runtime secrets. Generate a P-256 VAPID pair once and retain it: rotating it invalidates existing browser subscriptions. Only the public key reaches an authenticated client. Do not commit keys or browser subscription endpoints. Without the keys, the in-app bell still works and the panel explains that phone alerts are being prepared.

The encrypted push contains an alert ID only. The service worker fetches its generic text with the current session before displaying it, then checks again on click. The locked-screen text excludes names, property addresses, bank details, amounts and message contents. A missing/wrong/expired session or offline fetch produces generic account-free text and opens the notification center. Clicking a valid bill alert opens that bill with the current balance and direct owner payment options. Old or resolved alerts cannot change a balance or initiate a transfer.

Turning off notifications deletes the current server subscription, unsubscribes the browser and closes displayed notifications. Normal sign-out removes the server device subscription and clears its HttpOnly device cookie. A temporary database failure must not block session sign-out; any remaining queued push still needs the signed-in account to reveal text. Browser permission itself is managed by the browser. Reconnect explicitly after signing back in.

## Delivery and free-test limits

Payment records and notifications are created together by D1 triggers, so a notification failure cannot turn a successful report into an unreported payment. Notifications stop being inserted at 10,000 stored prompts; rental/payment writes continue. Scheduled cleanup removes notifications after 60 days and their delivery records after seven days. Original rental and payment history is preserved. Devices expire after 90 days without renewed device settings. Limits are three devices per account, 500 devices globally and 20,000 queued delivery records. Delivery runs immediately after supported mutations and retries on the existing Cron. The billing job checks at most eight due schedules per pass, leaving room for notification work under the free per-invocation request limit. At most six device deliveries run per pass, each with a short exclusive lease and at most three attempts. Successful devices are not retried because another device failed. Expired endpoints are removed. Browser push expires after 24 hours if it cannot be delivered. Browser delivery is best effort and may be delayed by connectivity, battery policy or disabled permission.

Only HTTPS Google FCM, Mozilla and Apple push endpoints are accepted; outbound redirects are not followed. The app cannot send to arbitrary URLs. Notification, enrollment, device-cookie and read-status APIs require the current verified account and reject cross-site writes. Subscriptions cannot be taken over by another account, even if a caller supplies the endpoint. Names and bank details are never included in push payloads.

## Verification

`npm run check` and `npm test` include actual SQLite migrations/triggers, Philippine reminder dates, pending/settled/cancelled/closed suppression, independent Node-crypto decryption of the Web Push wire format, verified VAPID signatures, concurrent claims, per-device retries, opt-in timing and service-worker account switching/deep links.

After a production build, `node scripts/notifications-smoke-test.mjs` starts a separate loopback Worker on port 5189 with a new isolated D1/R2 state directory. It checks listing upload/submission/review, inquiry and reply, original-account rental offers, acceptance, actual bill creation, owner receiving details, renter reporting, owner confirmation, balance/history, notification privacy/read state and device enrollment/opt-out/sign-out. An intentionally invalid local VAPID private key prevents outbound delivery. The runner removes only its own isolated state.

The physical Android permission/lock-screen check requires a device and user permission. Open the deployed site, sign in, open the bell, enable notifications and select **Send test alert**. Verify the alert with the app in the background and tap it. Then turn alerts off and confirm the device is disconnected. Backend and service-worker tests do not prove delivery to a real phone.
